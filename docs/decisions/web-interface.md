# Web interface technology

Status: proposed (M1, issue #191). Decided with txoof.

## Problem

In v2 the web interface is the main way to set up and change PaperPi: plugins, screen, password. A command line is used only where it really can't be avoided. It runs on the Pi, so it must be light enough for a Pi 3. PaperPi is a household device on a home network, so the web interface is kept simple.

## Options considered

1. **FastAPI, with pages built on the Pi plus htmx.** FastAPI is a Python web framework built on pydantic, the package that already describes and checks the config (`config-format.md`), so forms can be built straight from those descriptions. The Pi sends ready HTML pages. htmx is a small JavaScript file (about 15 KB) that updates one part of a page without reloading it. No build step, no Node.js. Uses roughly 40–60 MB of memory. **Chosen.**
2. **Flask.** An older Python framework. Similar, but it doesn't link to pydantic as neatly.
3. **A JavaScript app (React, Vue).** Richer pages, but it needs a separate build step with Node.js, a second programming language, and more memory and processor time on a Pi 3.

## Decision (proposed)

### Pages

- Pages are built on the Pi. htmx updates parts of a page, such as the screen preview and the list of warnings.
- A page that needs dragging or resizing gets a small JavaScript library made for that, loaded as a plain file with no build step. The first case will be the dashboard editor (see "Later").

### Plugin list pages

*Added in M5 part 2b (issue #238), agreed with txoof on 2026-10-07.*
- **Active Plugins** lists every `[[plugin]]` block in the config file, in file order (the order the plugins take turns), also blocks with errors. Each has: Switch on / Switch off, **Up** and **Down** buttons (no dragging, so no extra JavaScript library; works the same on a phone), and Remove, which asks first. *Update (M5 part 4, 2026-10-11): the Home page took over this list (PR 3 of part 4) and adds dragging as well as the buttons; `/plugins` now opens the Home page. See "Look, menu and pages" below.*
- **Plugin Library** lists every plugin type that comes with PaperPi, with its one-line description, except `default` (PaperPi's own "nothing to show" message) and `debugging` (for testing PaperPi). Choosing one asks for a name (a free one is suggested, for example "Clock 2"; it may be left empty) and adds the block at the end of Active Plugins (now the Home page's list) with a new `id` (see `config-format.md`, M5 part 3a-0). Active Plugins shows the name, and the `id` next to the type when it differs, so two plugins with the same name can be told apart. Each has an example picture (see "Preview images").
- A plugin with required settings (see `plugin-interface.md`) is added **switched off**, and the add page lists those settings with their help text (for `met_no`: a real email address, as met.no's terms ask). Active Plugins shows "Needs settings: ..." (on the Home page from part 4: "Configuration Required") and can't switch it on until they are filled in. *M5 part 3a-2 (agreed with txoof on 2026-10-08):* after adding, the new plugin's settings page opens at once, and each plugin in Active Plugins (now on the Home page) has a Settings link. The settings page also has a folded "Technical information" part with the plugin's `id`, type and storage folder.
- Each change is saved at once (nothing else in the config file changes: comments stay, and the comments just above a `[[plugin]]` line move and are removed with its block; a comment on the same line as a setting that changes, such as `enabled =`, is lost) and PaperPi reloads the file, so it applies at once.
- **Hand edits not applied yet:** a change from the web interface is made to the file as it is on disk, so hand edits stay and apply together with it. The page then says "Your hand edits to the config file were applied too." (The other choice, refusing to save until the hand edits are applied, needs an extra step every time.)
- A change names its block by place and `id`. If the block was moved or its `id` changed by hand since the page was shown, nothing is changed and the page says the file changed meanwhile. A file the web interface can't change safely (for example a `[[plugin]]` line written in an unusual way) is never saved wrongly: every change is read back and compared before saving. A change is also refused while the file has a problem that stops PaperPi from using it (PaperPi then runs on the last good copy, so the change would not apply), and when the file would become larger than PaperPi reads.

### Plugin settings forms

- One page handles every plugin. It reads the plugin's settings description (see `plugin-interface.md`) and builds the form from it: number field, dropdown, password field for API keys, and so on.
- On Save, the values are checked with the same description. Errors are shown next to the field. A saved change applies at once (see `live-config-reload.md`).
- A setting that needs more than a plain field can name an input type from a small list in the web interface, e.g. `location` (lat/lon lookup), `server_search` (find music servers), `layout_picker`. New input types are added when a plugin needs one. *Built in M5 part 3a-2:* a plugin names one with `paperpi.plugin.setting(..., helper="location")`; the web interface's list (`paperpi.web.helpers`) holds a function per name that adds its part under the field. A name it doesn't know adds nothing, so the plain field still works. The first helper is `location` (part 3c).
  - *Update (M5 part 3c, 2026-10-10):* replaced by setting helpers: a helper is a function of the plugin that returns choices as data (PaperPi offers shared searches, such as a place search, for helpers to call), and the web interface shows one standard search box and pick list for all of them. See `setting-helpers.md`.
- Plugins added later show up without changes to the web code.
- *Agreed with txoof on 2026-10-08 (M5 part 3a):* the page shows the plugin's `name` first, then its own settings, then display time, refresh, layout and level; the other shared settings (time limit, alert and storage settings) are folded under "More settings", which opens by itself when one of them has an error or a value that is not the default. Each field shows its value, or the default when the file doesn't set it.
- How a save works (M5 part 3a-1): only settings that changed are written. An empty field means "the default" (an empty check box: off; an empty list: nothing picked); a value changed to the default is taken out of the file and becomes the comment `# key = default` again (a value left as it is stays, also one written in the file that equals the default), so the help text above it still fits. A new setting takes the place of its `# key = ...` comment line when there is one. If any value has an error, nothing is saved; each error is shown next to its field, with what was typed (never a secret). A secret (such as an API key) is never shown on the page; leaving its field empty keeps the saved one. A setting the form can't show (a group of settings, a list of numbers) is shown as it is in the file, to be changed there. A setting written over several lines in the file is never changed by the page.

### Logging in

- The first person to open the web interface sets the password. After a reset (delete the password line in the config file, see `config-format.md`) the same happens again. This replaces "password set during installation" in the plan; installing needs no extra step.
- After logging in, the browser stays logged in for 1 year, using a cookie (a small token the browser keeps). There is a **Log out** button.
- No limit on wrong password attempts.

*Update (M5, issue #238, agreed with txoof on 2026-10-07):*
- The web server runs **inside `paperpi run`**, in its own thread, not as a separate program. It can tell the scheduler directly to apply a change, it needs one Python process fewer (about 40 MB), and there is one program to install. Previews draw in a separate process with a time limit, like normal updates, so a slow or broken plugin can't stop the web pages or the screen. If the web interface can't start (port taken), the log says why and the screen keeps running.
- The password is stored as a **scrypt** hash, which is built into Python (about 0.1 s and 16 MB of memory per check on a Pi; checks run one at a time; no limit on wrong tries, agreed again on 2026-10-07). The log-in cookie is signed with that hash, so a new password logs out every browser.
- Packages: FastAPI, uvicorn (the web server that runs FastAPI), jinja2 (page templates) and python-multipart (reads forms).
- **Log-in can be switched off:** `login = false` in `[web]`. Then anyone on the home network can change the settings; the config check gives a hint and the home page says so.
- **Forgotten password:** `sudo paperpi reset-password` removes the `password_hash` line and leaves the rest of the file as it is. After a restart or reload, the first visitor sets a new password. The log-in page shows these steps.
- Forms are only accepted from the web interface's own pages, and its pages can't be shown inside another website. Without this, a web page on the internet could make the visitor's browser send a form to PaperPi in their name. For the same reason the web interface only answers when it is opened by an IP address (e.g. `http://192.168.1.20:8080`) or `localhost`: a web page could otherwise point a name of its own at the Pi (called DNS rebinding) and set the first password itself. Names such as `paperpi.local` may be allowed later. Agreed with txoof on 2026-10-07: setup is done by IP address.

### No HTTPS

- The web interface uses plain HTTP, e.g. `http://paperpi.local:8080`. HTTPS (an encrypted connection) needs a certificate, and without a public one browsers show a warning page, which only gets in the way at home.
- The docs say: the web interface is for the home network only. Do not open it to the internet.

### Preview images

- **Home page:** a copy of what is on the e-paper screen now, with the plugin's name and when it was drawn. It updates by itself when the screen changes.
- **Plugin settings page:** a **Preview** button draws the plugin with the settings in the form, before saving, in a separate process, as normal updates are drawn. The real screen is not touched. If the plugin's data source can't be reached, the preview uses the plugin's sample data and says so.
- *Update (M5 part 3b-1, agreed with txoof on 2026-10-09):*
  - The preview draws the block as Save would write it (the form's values applied to a copy of the file text), at the screen's size and for the screen's type from `[display]`, as the screen runs now (a change of type, model, size or mode applies at the next start, also for previews; rotation and `color` apply at once). It runs in its own process with a time limit, as normal updates do, in a new, empty storage folder that is deleted afterwards, so it can't change the plugin's saved files.
  - Real data may take the plugin's own time limit, but at most 45 seconds. When it fails, takes longer, has nothing to show right now, or a required setting is still empty, the preview draws the plugin's sample data (at most 10 seconds) and says why.
  - One preview is drawn at a time; a second one meanwhile is asked to wait.
  - The picture is sent inside the page (a `data:` address), so it is never saved as a file. The pages allow such pictures (`img-src 'self' data:`).
  - For later plugins: an empty secret field (such as an API key) keeps the saved secret, also in a preview. A plugin that has both a secret and a web address the user can change must not send the saved secret to a changed address: then the secret must be typed again (in a preview and when saving), or the plugin allows only its own servers. Network errors in the preview should then say only "could not reach the server", so the preview can't be used to look around the home network. No plugin has such an address yet (checked in the security review of part 3b-1); this matters for e.g. the Dutch public transport plugin.
  - There is no "send to display" button on the settings page. A **Show on screen now** button, which starts a saved plugin's turn at once, comes with the home page in part 4 (named **Show now** there).
- **Plugin Library:** each plugin has an example picture, drawn with its sample data. *Agreed with txoof on 2026-10-10 (M5 part 3b-2):*
  - The plugin's name and its picture both open the Add page (no separate Add link). Since Library refresh B2 they open Look closer instead, and **+ Add** opens the Add window. The pictures are drawn ahead and saved in `library-pictures/` in the state folder, so the page opens at once. They are drawn at the screen's size from `[display]`, in the best gray (256 shades) so they are easy to see on a phone, also for a black-and-white or 4-gray screen; a color screen keeps its colors (txoof, 2026-10-10). They use the plugin's default settings and first layout (since Library refresh B2: every layout, the first layouts of all plugins first), one at a time, each in its own process with the 10-second sample time limit. Drawing starts a minute after PaperPi starts (so the first screen update goes first), or at once when the Library page is opened or the config file is loaded again. A change of the screen's type, model, size or mode applies at the next start, as for the screen itself.
  - Each file name holds a fingerprint: a short code made from the name, size and time of last change of every file in the plugin's folder, the screen's width, height and type, and the PaperPi and epdlib versions. A new or changed plugin, or another screen, gives a new name, so its picture is drawn again; pictures that match nothing any more are deleted. The files' contents are not read, as that is too slow for the 19 MB of moon_phase images on a Pi 3. Only files in the plugin's own folder count; a change to PaperPi's shared code counts only through the PaperPi version. The browser may keep a picture for a day; a new picture has a new file name.
  - While a picture is missing, the page shows "Drawing the example picture…" and asks again every 3 seconds (htmx) until it is there. A plugin that takes longer than 10 seconds (the Pi may just be busy) is tried up to 3 times. Any other picture that can't be drawn says why, and is not tried again until the plugin, the screen or PaperPi changes (or PaperPi starts again), so an open Library page can't keep the Pi busy. If the folder can't be written, every plugin says so.
  - A plugin whose code is changed while PaperPi runs gets a new picture (each picture is drawn in a new process), but the Library's list and a plugin that was broken at the start only change after a restart, because the web interface loads each plugin's code once.

### Look, menu and pages

*Agreed with txoof on 2026-10-11 (M5 part 4), using clickable mockups of each page.* The first PR of part 4 built the look, the menu, the Dark/Light button and the ways back; the third the Home page. Everything else here is built in the later PRs listed in issue #238; until then the pages work as described in the sections above.

**Look (every page)**
- One set of colours, with a light and a dark version. The page follows the device's light or dark setting; a **Dark/Light** button in the menu overrides it, and the browser remembers the choice (in its own storage for this site, `localStorage`). Without JavaScript the button is hidden and the page follows the device.
- Status labels use colours from the Okabe-Ito set, which people with the common kinds of colour blindness can tell apart, and always have a symbol or text as well, so they can be read without colour.
- System fonts only: nothing is loaded from other servers, so the pages work without internet and keep the strict `Content-Security-Policy` (no inline scripts or styles).
- **One width on every page** (#282, 2026-10-14): the menu bar, the page and the footer are 64rem wide everywhere, so the menu and the left edge don't move when switching pages. Pages of forms or text (Settings, Add, Remove, Log in, ...) keep their lines short with a narrower content (46rem) that starts at the same left edge; Home, the Plugin Library (a grid of pictures, more per row; txoof, 2026-10-14) and the Warnings pages use the full width, with their paragraphs of text kept at 46rem. Room for a scroll bar is always kept (`scrollbar-gutter: stable`), so a page without one doesn't shift sideways either.
- **Menu** on every page after logging in, with the current page marked. Now: Home · Plugin Library · Warnings (Active Plugins left the menu when the Home page took over its list, part 4, PR 3; Warnings came with its Full log tab in PR 4a, and got its Warnings tab in PR 4b). Screen & system joined in part 5 (PR 5-1). On a phone it folds into one **☰ Menu** button (built with the browser's own fold-out element, `<details>`, so it needs no JavaScript), which also shows the number of things that need attention. A page one step down starts with a way back, e.g. "Home › Weather Berlin".

**Home page** (replaces the Active Plugins page)
- At the top, the picture that is on the e-paper screen now, upright as people see it (before rotation), with the plugin's name, since when it is shown and what comes next. It stays at the top while the plugin list scrolls, and shrinks to a slim bar (small picture and name, "Show bigger") while scrolling down. The page keeps its height meanwhile (the room the panel gives up is added below the list, and the browser's own "scroll anchoring" is off on this page), so a page only a little taller than the window does not jump back to the top (#285). It asks for a new picture every few seconds only while the page is open, and downloads it only when it changed.
- Buttons next to the picture: **Skip to next** (end this turn), **Refresh** (fetch new data and draw this plugin again), and **Dismiss alert** while an alert is shown.
- Below it, a card for every plugin, as a list or as a grid (a switch; the browser remembers it). Each card shows its place in the order (1, 2, 3 …; in the grid it runs left to right, then on to the next row), the plugin's last picture (before it has one: the Library's example picture, faded and marked EXAMPLE), its name and type, and a status: ▶ On screen now, → Next, ↻ In rotation (with "shows in about N minutes"), ○ Off, ! Configuration Required, ⏸ Paused due to errors (with when it is tried again).
- Card buttons: **Show now**, **Settings**, an on/off switch, and up/down arrows (left/right in the grid). **Change order** shows a handle on each card's left edge to drag the card by (with SortableJS, a small JavaScript library for dragging, shipped with PaperPi like htmx); each move is saved at once.
- **Show now** gives the plugin one extra turn of its full display time; then the order goes on as planned (the plugin that was next is still next). What every button does in the scheduler (also over an alert, without a picture, Skip on an interrupt, Refresh drawing in full): see "Controls from the web interface" in `plugin-scheduling.md`.
- *How it is built (part 4, PR 3, 2026-10-11):* `paperpi run` hands the scheduler to the web interface, which reads its summary (what is on screen, what comes next, how each plugin is doing) and passes the buttons on to it. The screen part of the page (`/now`) asks for itself again every 3 seconds with htmx, and brings each card's status and picture along (htmx "out of band" parts: one answer updates several places on the page), so a card being dragged is never replaced. The pictures are PNG files made only when a page asks for them; their address holds a number that changes with the picture, so the browser keeps a picture and fetches it again only when it changed. Card pictures are made at most 640 pixels wide or high. Dragging uses SortableJS 1.15.6 in its mode with mouse and touch events (the browsers' own dragging works differently in each browser); each drop or arrow press saves at once, and the page numbers the cards again without loading. With a file that changed meanwhile, the page says why and loads the list as it is now. Without JavaScript the page still works: the screen part doesn't update by itself, the arrows and buttons are plain forms, and there is no grid or Change order.
- The built-in pictures have plain names on the Home page: "Splash Screen", "Clock (no plugin is ready yet)" and "PaperPi message" (the `default` plugin). A plugin that was switched on a moment ago, before PaperPi has loaded the file again, says "PaperPi is loading the change."

**Warnings page**
- **Needs attention now:** problems that are true now, each with a button that helps: a plugin paused due to errors (**Try again now**), Configuration Required (**Settings**), a mistake in the config file (with its line), the screen not answering (**Try again now**). The number in the menu counts only these, so it goes away by itself when they are fixed.
- **Recent warnings and errors:** the last 100, grouped by day, in plain words, with a filter (errors, warnings, where they came from) and the exact log line under "Technical details".
- *How the Warnings tab is built (part 4, PR 4b, 2026-10-14):* the menu's Warnings opens `/warnings`; the Full log is its second tab. "Needs attention now" is made from the scheduler's summary and the config file's plugin blocks, in this order: a config file PaperPi could not use (the scheduler keeps why in `Summary.config_errors`, at the start on the last good copy and at each reload; empty again after a load that works; without the scheduler, the problems the web interface finds in the file) with **Load the file again** (asks for the same reload as `kill -HUP`); the screen not answering (**Try again now**); then, in config order, each plugin whose Home card says "Paused due to errors" (**Try again now**, **Settings**), "Configuration Required" or "Not used: has errors" (**Settings**). The buttons are plain forms that open the tab again with a short message. The number next to Warnings in the menu (and on the ☰ Menu button) counts these; it is hidden at 0. Changed after the mockup (txoof, 2026-10-14): the recent list shows the log lines as they are, with the name of the part of PaperPi that logged them, not a plain-words text per line (a traceback is folded under "Traceback"); and it has no "where they came from" filter, only All / Errors / Warnings, since a plugin's failures are logged by the scheduler, not by the plugin (the Full log's search finds every line about a plugin). The lines come from the same kept lines as the Full log, so the ones in the log file survive a restart. While the tab is open, htmx asks for it again every 10 seconds and replaces it (and the menu's number) only when something changed.
- A **Full log** tab: every log line, with a filter by level, search, new lines while the page is open, and **Download log** (a text file with every line). Warnings, errors, starts and stops, crash details and the hourly health line are also kept in a small file in the state folder (at most about 2 MB), so they survive a restart of the Pi; the other lines are kept in memory only (the last 5,000). This keeps SD card writes to a few kilobytes a day. Rejected: keeping the system log on the SD card (Raspberry Pi OS keeps it in memory on purpose, and it is shared by every program), and a log of PaperPi's own inside the system log (only works when PaperPi runs as a service started by systemd, and the web page can't easily read it). This changes the "Logs" part of `errors-and-time-limits.md`. Passwords and secret settings never go into the log.
- *How the Full log is built (part 4, PR 4a, 2026-10-12):* the page (`/log`) is made on the Pi from the kept lines (`paperpi.logbook`): the lines from the log file first (from before the last start, marked "PaperPi started again …"), then the ones in memory, oldest at the top, scrolled to the newest at the bottom. The level filter (Everything / Info and up / Warnings and errors; Everything only adds DEBUG lines when PaperPi runs with `--verbose`), the search (any case; what it finds is marked) and the "New lines as they come" box are one form: with JavaScript, htmx sends it at every change and replaces only the list; without JavaScript, a **Show** button sends it. The page shows at most the newest 1,000 lines that match, so a phone doesn't get a page of megabytes; **Download log** gives every kept line as a text file, as in the log file. While "New lines as they come" is on, htmx asks every 3 seconds for the lines after the newest one shown and adds them at the end (a filter change cancels a request still on its way); the list stays at the bottom unless someone scrolled up to read, and the oldest lines go once there are more than 1,000. A search that hides every line from the file also hides the "started again" mark.

**Hand edits to the config file**
- A bar on every page: "The config file was changed outside the web interface. The changes are not used yet.", with **Review changes**.
- The **Review changes** page lists the changes per plugin and for the screen settings (old → new), each with a link to its settings page (for the screen: once the Screen & system page exists, part 5), and offers **Apply changes** and **Undo hand edits** (after "Are you sure?"; the edited file is kept as `paperpi.toml.undone`). With a mistake in the file it shows the line and Apply is off. It also shows how to apply from the command line (`sudo systemctl reload paperpi`, or `kill -HUP <process id>`, which sends PaperPi the reload signal). A `paperpi reload` command is planned in issue #272.
- *How Review changes is built (part 4, PR 5a, 2026-10-15):* the web interface keeps the text of the config file PaperPi loaded last (at the start and at each reload that could be used). The file has hand edits when its settings differ from that text and it is not the text the web interface saved itself; a change to a comment or a blank line alone is not one. The page compares the two as TOML reads them: per `[[plugin]]` block, matched by its ID (a new ID is a removed plugin and a new one), then `[display]` ("Screen"), `[web]` and the rest of the file. Each changed setting shows its old and new value as written in the file, or "(default: …)" when it is not set; secrets (the web password, a plugin's password or API key; for a plugin type PaperPi doesn't know, every setting but the shared ones, and after a type change also the old type's secrets) show only "(hidden)". Notes say what is special: a screen or `[web]` setting that applies at the next start, a new plugin's place in the order, a plugin moved among the others (the fewest plugins that explain the new order; one only pushed along by an added or removed plugin did not move), a removed plugin's storage folder (kept, as it may hold photos). A file that can't be used shows its mistakes with their line, and **Apply changes** is off (and refused when sent anyway); a mistake in one plugin block is listed, but Apply stays on (PaperPi leaves that plugin out). **Apply changes** asks for the same reload as `kill -HUP` and waits up to 3 seconds for PaperPi to load the file, which it does between two screen writes; the page then says "Applied", or that it is still busy. Without the screen running (`paperpi run` not running the scheduler) there is nothing to apply to, so there is no bar. The command shown is `sudo systemctl reload paperpi` when PaperPi runs as a service (systemd sets `INVOCATION_ID`), else `kill -HUP` with PaperPi's process ID. The mockup's **Copy** button next to the command is left out: the page has no script of its own, and the command is short to type or select.
- *How Undo hand edits is built (part 4, PR 5b, 2026-10-15):* **Undo hand edits…** opens "Undo the hand edits?" on the same page (`/changes?undo=1`, a plain link, so it works without JavaScript), with **Undo hand edits** and **Keep them**; the box names the full path of the `.undone` file and says an older one there is replaced. The form carries a short mark (a hash) of the edited text the page showed: if the file changed again after that, Undo is refused with "The config file changed after this page was opened", so it never undoes edits the user has not seen. Undo first saves the edited file as `<config file name>.undone` in the config file's folder (replacing an older one; for a config file that is a link, next to the file it points to), with the config file's permissions and owner, then writes back the text PaperPi loaded last. PaperPi uses that text already, so nothing loads again. If either file can't be saved, the page says so and the config file stays as it was. The `.undone` file always goes in the config file's folder: saving the config file itself needs that folder to be writable (the new file is written there first, then renamed), so another place would not help. A file with a mistake can be undone too; that is when Undo helps most. Undo is refused when there is nothing to undo (no hand edits, only a comment changed, or the screen is not running). One rare case is left: after **Apply changes** said PaperPi is still busy, an Undo can be written just after PaperPi read the edited file. PaperPi then uses the edits while the file holds the old text; the bar comes back and shows the change the other way round, so nothing is hidden or lost.

**Plugin Library**
- A card per plugin: example picture, a plain name (a new `title` in the plugin's definition, e.g. "Weather"; the type is shown small), the description, labels ("Uses the internet", "Configuration Required"), the names it was already added under, a search box, and **+ Add**.
- *How the cards are built (part 4, Library refresh A, 2026-10-15):* the label texts are txoof's: **Requires setup** (the plugin has required settings, so it is added switched off, or needs something set up outside PaperPi first: a new `setup` sentence in its definition, shown on the card and the Add page; Spotify needs go-librespot, LMS a music server; txoof 2026-10-15, with a "How to set it up" link to the README), **Requires internet** and **Uses home network** (a new `network` field in the plugin's definition: `"internet"` or `"home"`, e.g. the LMS plugin talks to a music server at home; Spotify gets "Requires internet", txoof 2026-10-15, as it fetches covers from Spotify and plays nothing offline). The mockup's "For testing" label is left out, as the `debugging` plugin stays hidden from the Library. Cards are sorted by title. The title also starts the suggested name ("Weather 2") and heads the Add page. "Added:" lists the names from the config file per type (left out when the file can't be read). The search box needs JavaScript (`library.js`; hidden without it, and then every card shows): it keeps the cards whose title, type, description or labels hold every word typed, and says "N of M plugins". Every card links to the plugin's **README**, shown by PaperPi itself (`/library/<type>/readme`, txoof 2026-10-15: works without internet and matches the installed version; GitHub was the other choice). The README is Markdown, turned into HTML with the `markdown-it-py` package (CommonMark plus tables; HTML in the file is shown as text). Left out: the first heading (the page has the title), pictures and the "Sample images" section (`tests/images/` is not installed), and what is left empty without them. Links to other plugins' READMEs open their page; links to websites stay; other links (source files) become plain text.
- **Look closer:** a larger view with a button for every layout. Layouts also get a plain title ("Next 12 hours"), shown in the Library and on the settings page, with the code name small. A picture is drawn ahead for every layout; a layout for upright screens is drawn upright, with a note (see B2 below).

A layout without a title is shown by its name. The Library card lists the layout titles (for a plugin with more than one; the search looks in them too) and the settings page's layout list shows "Every 3 hours (steps_3h)". The plugin's title replaces its type on the Home cards, the "On the screen now" panel, the settings page and the Remove page; the settings page's Technical information keeps the type. Refresh B was split in two PRs (txoof 2026-10-20): B1 the titles and the Add window, B2 the pictures for every layout and Look closer.
- **+ Add** opens a small window (name, whether it needs settings first); without JavaScript it falls back to the Add page.
- *How the Add window works (part 4, Library refresh B1, 2026-10-20):* `library.js` asks the server for the Add form (the same `_add.html` the Add page uses, so the two never differ) and shows it in a `<dialog>`: the suggested name ("Weather 2", selected so typing replaces it), the settings to fill in first (or "It is added switched on, at the end of your list"), Add and Cancel. Escape, Cancel or a click next to the window closes it. Add sends the form as the Add page does, and the plugin's settings page opens. A name that can't be used, an unknown plugin or a log-in that ran out opens the whole page that says why. Without JavaScript, **+ Add** opens the Add page. Pictures: `docs/images/web/add-window-light.png`, `add-window-phone.png`.

In the Library it opens in the same window as the Add form (`library.js`; a layout button loads the window again, **+ Add** in it shows the Add form); without JavaScript it is its own page, `/library/<type>/look?layout=<name>`. **Screen & system page** (part 5)
- Sections, every one saying when its settings apply (at once, or at the next start): Screen (**Change screen…**: type, model and VCOM (the voltage printed on the screen's ribbon cable) together, then the steps to swap it; the previous screen is kept, to go back if the new one doesn't answer), Picture (rotation as four small pictures, colour), Screen care, Splash Screen & Fallback Plugin, Web interface, and This Pi (version, running time, memory, disk, temperature).
- *Saving (part 5, PR 5-1, txoof 2026-10-23):* the first build had a Save in each section, and txoof found it clunky: a forgotten Save lost the change without a word. Now the whole page is one form with one **Save and apply** (txoof's idea; mockup https://claude.ai/artifact/D5iPcpw3faUYarmo5eQfah). A changed setting is marked and says what PaperPi uses now ("Not saved yet (now: 0°)"); a bar at the bottom of the window counts the changes and has **Undo changes** and **Save and apply**; a link to another page asks "Leave without saving?" (**Save and apply, then go**, **Leave without saving**, **Stay on this page**), and closing the tab gets the browser's own warning. A wrong value saves nothing and is shown in red next to its field. Without JavaScript the page has a plain Save and apply button. A setting set back to its default is taken out of the file (it becomes `# key = default`), and a setting that did not change keeps its line as written. The other choice was saving each setting as soon as it changes.
- *What PR 5-1 has:* Screen (what PaperPi uses now: type, model, VCOM, state; to change it, the page pointed to the config file until **Change screen…** came in PR 5-2), Picture, Screen care, Splash Screen & Fallback Plugin, and This Pi (version, running time, last screen write, memory, free disk, processor temperature, measured again every 30 seconds while the page is open). Restart PaperPi came in PR 5-2; the Web interface section comes in PR 5-3. Review changes links its Screen changes here. Pictures: `docs/images/web/system-light.png`, `system-changed-light.png`, `system-leave-light.png`, `system-phone.png`.
- *Change screen and Restart (part 5, PR 5-2, txoof 2026-10-23; mockup https://claude.ai/artifact/SXxjtzxZkTQoC3mar2H7o1):* **Change screen…** in the Screen section opens a page of its own: the type, then for an IT8951 board the model and VCOM, for a virtual screen the size and what it shows. A new type, model, size or mode is used from the next start of PaperPi; a new VCOM for the same screen applies at once. After saving a new screen, Screen & system shows a yellow box, "Saved, waiting for a restart", that names the new screen. For an IT8951 board it lists the steps to connect it with the power off (`sudo shutdown now`, wait for the green light, unplug, connect, power on). For a virtual screen it offers **Restart PaperPi now**. Either way it offers **Undo: keep the current screen**, which writes the screen in use back into the file. The screen in use is kept in `previous-screen.toml` in the state folder (txoof chose this over comments in the config file). When the new screen does not answer after the restart, the Screen section offers **Go back to the previous screen…**, which saves the kept screen again and restarts (pictures: `docs/images/web/change-screen-light.png`, `system-waiting-light.png`, `system-restart-phone.png`). The kept screen is removed after Go back or Undo, and once the new screen answers. A second new screen saved while the first one does not answer keeps the screen that worked. The confirm steps ("Restart PaperPi?", "Go back…?") are a box on the page itself (`/system?restart=1`, `/system?back=1`), so they work without JavaScript.
- *How Restart works (txoof 2026-10-23):* the service runs as the `paperpi` user, which can't run `systemctl`, so PaperPi ends itself with exit status 75 and the service file starts it again: `SuccessExitStatus=75` (a clean stop, not a failure in the log) and `RestartForceExitStatus=75` (started again although `Restart=on-failure`). A restart keeps the picture (no clear at the stop). PaperPi counts as a service when systemd set `INVOCATION_ID`. The Restarting page asks for `/system/pi` every 2 seconds and opens Screen & system again once PaperPi was gone and answers again; without JavaScript it opens it after 30 seconds. The other choices were `Restart=always` (also starts PaperPi again after any other clean exit) and exit status 1 (logged as a failure and counted towards the 5 starts in 10 minutes).
- *Web interface section (part 5, PR 5-3a, txoof 2026-10-23; mockup https://claude.ai/artifact/UMzoUY3LJdHm5KzfvQipVZ):* the section shows the address in use, then **Port**, **Reachable from** (every device on the home network, or only this Pi; an address set by hand in the file stays a third choice) and **Password** ("Ask for a password"), all part of the one Save and apply. Port and address are used from the next start: Screen & system then shows a yellow box, "Saved, waiting for a restart", with the new address, the last-resort command `paperpi web-defaults`, **Restart PaperPi now** (as a service) and **Undo: keep the current web settings**. A new port is tried on the Pi while it is typed (`/system/port`, htmx) and again when saving: a port in use by another program, or below 1024 (needs administrator rights, which the service doesn't have, also when PaperPi was started with sudo), is refused in red, and Save and apply is greyed out. The port in use now is not tried (PaperPi holds it itself), unless the address changes from one that is not "every device". After a restart to a new address, the Restarting page opens the new address after 30 seconds: it can't ask the new address whether PaperPi is back, because the page may only ask its own address. The password switch applies at once. Switching it on again always removes a password kept from before, so the next page is **Set a password** (txoof chose this over keeping the old password). **Change password…** asks for the current password and the new one twice; other browsers are logged out (the cookie is signed with the password hash), this one stays logged in. `paperpi web-defaults` takes `port` and `address` out of `[web]` (back to port 8080 for every device) and keeps the rest. Part 5-3b adds **Keep these settings** after a restart to a new address.
- *Keep these settings (part 5, PR 5-3b, txoof 2026-10-24; mockup https://claude.ai/artifact/MtRfoyShBDBeN6VLT4UU1E):* saving a new address or port keeps the one in use in `previous-web.toml` in the state folder (like `previous-screen.toml`; Undo removes it). After the restart, a yellow box on **every page** (txoof chose this over Screen & system only) says "New web address", counts down 5 minutes (`limits.KEEP_WEB`; `static/keep.js`, without JavaScript it shows the time left when the page was opened), and offers **Keep these settings** and **Go back to port 8080 now**. When nobody presses Keep, PaperPi writes the old address and port back into the config file and moves the web interface there inside the running PaperPi (the uvicorn server stops and a new one listens at the old address; the screen keeps running, and it works the same when PaperPi was started by hand). The old address is opened before the config file is written: when another program took it meanwhile, the web interface stays at the new address, Warnings says so, and the kept file stays for the next start. When the new port can't be opened at the start, it goes back at once. Either way, Warnings shows "The web interface went back to its old address" with the reason and an **OK** button, and the log has a warning line. While new settings are on trial, a further new address keeps the old one (the one known to work); going back then drops the further address, and Warnings names it. Pressing Keep in that case keeps the address in use as the way back from the further one. A restart during the 5 minutes starts them again: the kept file is still there (also when PaperPi keeps restarting after errors, so then it never goes back by itself). `paperpi web-defaults` removes the kept file first (or the next start would put the defaults on trial and go back to the old address); when PaperPi runs meanwhile and finds the kept file gone, it does not go back. The box and the Go back page say when the old address can only be opened on the Pi itself, and then don't open it in the browser. When the countdown reaches 0:00, the page opens the old address after 5 seconds. The "Go back" page opens the old address after 5 seconds; like the Restarting page, it can't ask the other address whether it answers.
- **Restart PaperPi** button (PaperPi ends; the service or Docker starts it again. When PaperPi was started by hand with `paperpi run`, there is nothing to start it again, so the button is not offered and the page says so). No button to shut down the Pi: that needs administrator rights, so the page shows `sudo shutdown now` to type on the Pi.
- A wrong port or address can't lock the user out: before saving, PaperPi tries the new port and refuses one that is in use or below 1024; after the restart, the new settings must be confirmed with **Keep these settings** within 5 minutes or PaperPi goes back to the old ones; as a last resort, a command on the Pi puts the web settings back to their defaults.

### Later

These wait until after 2.0, and each becomes its own issue then. Nothing in this design should block them.
- **Dashboard editor:** a graphical page to place and resize several plugins on one screen (milestones M9/M10). Dragging and resizing happen in the browser with a small grid library (e.g. gridstack.js). The Pi saves the result as a list of boxes (position and size of each plugin) in the config and draws a real preview after each change. Plugins already receive the size of the area they draw in, so they don't need changes.
- **HTTPS:** a docs page on putting your own web server in front of PaperPi for anyone who wants it. Docs only, no code.
